= KCPT - Kotlin Coroutines PostgreSQL Tasks
:toc: macro
:toclevels: 2
:idprefix:
:idseparator: -
:icons: font
:source-highlighter: highlight.js

[.lead]
PostgreSQL-backed message queues and cron for Kotlin coroutines — no broker, no scheduler daemon, just the database you already run.

KCPT turns a PostgreSQL database into durable background-work infrastructure.
`kcpt-message-queue` posts and receives typed payloads under a lease, with automatic retry and dead-lettering.
`kcpt-cron` fires a tick on a fixed schedule, exactly once across however many servers share the database, catching up in bounded chunks after downtime.
Both are built on the same primitives — a lease, a retry count, `LISTEN`/`NOTIFY` wake-up — so taking one never drags in machinery for the other.

.Main.kt — a message queue
[source,kotlin]
----
val sink = MessageQueueSink(source = dataSource.asSource())
val emails = sink.messageQueue("emails", EmailJob.serializer())

// Producer
emails.post(EmailJob(to = "user@example.com", subject = "Welcome"))

// Consumer
emails.workerPool { message ->
    sendEmail(message.payload)
    null // no notes to record
}
----

.Main.kt — a cron
[source,kotlin]
----
val cronSink = CronSink(source = dataSource.asSource())
val cleanup = cronSink.cron("cleanup", Cron.Config(interval = 10.minutes))

cleanup.run { from, to ->
    deleteOldRecords(before = to)
    null // no notes to record
}
----

No broker to run, no extra scheduler process, no polling loop.
Postgres notifies a consumer the moment work exists, and a cron tick stays on the clock across however many servers are listening for it.

== Why KCPT

*No broker.* Every guarantee below is built on PostgreSQL alone — `LISTEN`/`NOTIFY`, advisory locks, `FOR UPDATE SKIP LOCKED`, a `JSON` column.
If you already run Postgres, there is nothing else to deploy.

*Real-time wake-up, not polling.* A consumer parked in `receive()`, or a cron server parked between ticks, is woken by a database notification the instant work becomes available — not on the next tick of a poll loop.
A backstop timer exists for the case a notification never arrives, but it is a safety net, not the normal path.

*Lease, retry, dead-letter — built in, not bolted on.* A message or a cron window is leased, not locked forever: a crashed consumer's work is picked up by another one automatically, a failure is retried up to a limit, and a permanently failing one is dead-lettered and reported rather than retried forever.

*Cron ticks stay on the wall clock, concurrently.* A tick's window is computed once, from the schedule, and never shifted by how long a handler takes to run.
Different windows can be worked by different servers at the same time — a handler slower than its own interval does not stall the schedule, as long as another server is free to pick up the next tick.

*Every guarantee is written down.* Two long-form documents explain exactly how each guarantee holds, safeguard by safeguard, corner case by corner case: xref:docs/message-queue-algorithm.adoc[the message queue algorithm] and xref:docs/cron-algorithm.adoc[the cron algorithm].
This README is the front door; those documents are where "why can I trust this" actually gets answered.

=== A `Source`

Neither module opens a database connection on its own.
Both take a `Source` — literally `suspend () -> Connection` — and call it whenever they need one:

[source,kotlin]
----
public typealias Source = suspend () -> Connection
----

`DataSource.asSource()` adapts any `javax.sql.DataSource` — HikariCP, or an application's existing pool:

[source,kotlin]
.Main.kt
----
val hikari = HikariDataSource(HikariConfig().apply {
    jdbcUrl = "jdbc:postgresql://localhost:5432/mydb"
    username = "postgres"
    password = "postgres"
})
val source: Source = hikari.asSource()
----

IMPORTANT: KCPT depends on the PostgreSQL JDBC driver internally, but does not expose it as part of its own API.
Bring a driver and a connection pool the way an application already manages one — HikariCP is what both design docs' own examples use, but any `DataSource` works.


=== PostgreSQL

Nothing exotic: `LISTEN`/`NOTIFY`, `pg_advisory_xact_lock`, `FOR UPDATE SKIP LOCKED`, and a `JSON` column type.
Any reasonably current PostgreSQL server works — the test suite runs against Postgres 18.

``MessageQueueSink``'s and ``CronSink``'s schema setup each run once per process, lazily on first use, under their own advisory lock — so two processes, or two sinks in the same process, starting up at once never race each other into a duplicate `CREATE TABLE`.
They create their own tables independently (see <<project-layout>>) but share one `properties` table between them, tracking their own migration version in it separately.


=== JVM

KCPT is a JVM-only library, built and tested against a Java 17 toolchain.
There is no Kotlin Multiplatform target, and none is planned — the library is a thin, direct layer over `java.sql`.


== Core concepts — Message queue

=== `MessageQueueSink`

The entry point — one per application, or one per group of queues sharing a table prefix:

[source,kotlin]
----
val sink = MessageQueueSink(
    source = dataSource.asSource(),
    tablesPrefix = "public.kcpt_",   // the default
)
----

Schema setup runs the first time it is actually needed, unless an `initializationScope` is passed to run it eagerly instead.
`sink.messageQueue(name, serializer, config, messageObservers)` returns a `MessageQueue<T>` for one named queue, sharing the sink's tables and `Source`.


=== `MessageQueue<T>`

[cols="1,3",options="header"]
|===
| Member | Purpose

| `suspend fun post(value: T, due: Instant? = null)`
| Inserts a message — available immediately, or at `due`.

| `suspend fun tryReceive(): Message<T>?`
| One attempt: a leased message, or `null` if none is available right now.

| `suspend fun receive(): Message<T>`
| Suspends until a message can be leased, woken by `LISTEN`/`NOTIFY` the instant one is posted.

| `fun receiver(scope: CoroutineScope): Receiver<T>`
| A `receive()` that shares one listening connection across many calls — what `workerPool` uses underneath.
|===


=== `MessageQueue.Config`

[cols="1,2,3",options="header"]
|===
| Field | Default | Meaning

| `maxTries`
| `5`
| Attempts, including reclaims, before a message is dead-lettered.

| `securityCheckTimeout`
| `10.minutes`
| Backstop poll interval, for a message whose `NOTIFY` never arrived.

| `processingTimeout`
| `1.minute`
| How long a lease is held before another consumer may reclaim it.

| `processingGrace`
| `max(processingTimeout * .2, 200ms)`
| Extra margin before a reclaim, so a handler's own timeout always fires first.
|===


=== `workerPool`

The ready-made consumer loop: receive, dispatch, repeat, forever, across a fixed thread pool with a bounded number of concurrently in-flight messages.

[source,kotlin]
----
queue.workerPool(
    numberOfThreads = Runtime.getRuntime().availableProcessors(),
    numberOfWorkers = numberOfThreads * 4,
) { message ->
    // handle message.payload
    null // or a JsonElement of notes to record alongside a success
}
----

`workerPool` never returns — cancel its coroutine to shut it down.
See xref:docs/message-queue-algorithm.adoc#the-worker-pool[The worker pool] for why the receive-then-dispatch ordering is deliberate, not incidental.

A failure `process()` itself never got the chance to handle — the already-expired-lease `IllegalStateException` `process()` can throw before its own guarded region even begins, most concretely — is caught and reported through `onUnhandledFailure(message, cause)` rather than being left to cancel the whole pool; see xref:docs/message-queue-algorithm.adoc#safeguard-contained-unhandled-failure[the algorithm doc] for the full mechanism.


=== `Message<T>`

`tryReceive()`/`receive()` hand back a leased `Message<T>`.
It carries the payload, the lease's own timing, and every failed attempt so far:

[cols="1,3",options="header"]
|===
| Member | Purpose

| `val id: Uuid`
| The message's identity.

| `val payload: T`
| The decoded value passed to `post()`.

| `val receivedAt: Instant`
| When this lease was taken.

| `val expiresAt: Instant`
| When this lease nominally ends — moved forward by `extend()`.
Reclaimable by another consumer once `expiresAt + processingGrace` has passed, not at `expiresAt` itself.

| `val processingGrace: Duration`
| The queue's own reclaim margin — see the row above.

| `val notes: List<JsonElement>`
| Every note recorded by a previous failed attempt, oldest first.
|===

It is the caller's job to end that lease, one way or another, before moving on — either automatically through `process()`, or by calling one of ``Message<T>``'s own methods directly (see <<manual-processing>>).


==== `process()`

`Message<T>.process()` runs a handler against the message and guarantees exactly one write-back, whatever the handler does — this is how a message's lease should be ended, unless <<manual-processing,manual processing>> is genuinely called for:

[source,kotlin]
----
public suspend fun <T> Message<T>.process(
    timeout: Duration = this.expiresAt - Clock.System.now(),
    onFailure: (failure: MessageProcessingFailure) -> JsonElement = { JsonObject(it.defaultNotes()) },
    onRequeueFailure: (message: Message<T>, failure: MessageProcessingFailure, cause: Throwable) -> Unit = { _, _, _ -> },
    process: suspend (Message<T>) -> JsonElement?
)
----

[cols="1,1,3",options="header"]
|===
| Parameter | Default | Meaning

| `timeout`
| The lease's remaining time
| How long the handler may run before it is treated as a failed try.
Freely longer than the queue's own `processingTimeout` — when it is, or when the handover since receiving the message has already eaten into ``processingGrace``'s own margin, the lease is kept alive automatically for as long as the handler runs, up to `timeout`.
Throws `IllegalStateException` up front if the lease has already expired before the call even starts.

| `onFailure`
| Records the failure's default notes
| Produces the `notes` recorded alongside a timeout, a cancellation, or an exception — see `MessageProcessingFailure`.

| `onRequeueFailure`
| No-op
| Called if `failureRequeue`/`failureDelete` itself fails — a dropped connection, an exhausted pool — so that a database blip on one message's write-back can't propagate out and take the whole worker pool down with it.

| `process`
| _(required)_
| The handler itself.
Its return value is the `notes` recorded alongside a *success* — `null` for none.
|===

* The handler returns → `successDelete`.
* The handler fails → `failureRequeue`, immediately — which itself defers to `failureDelete` when that failure was the last authorized attempt.
* A `timeout` longer than `processingTimeout` — or a handover slow enough to have already eaten into `processingGrace` — has its lease kept alive automatically, for exactly as long as the handler runs.
No parameter to configure, and nothing to misconfigure (see xref:docs/message-queue-algorithm.adoc#safeguard-keepalive[the algorithm doc]).

A timeout, the caller's own cancellation, and a foreign `CancellationException` raised from inside the handler are told apart and handled correctly — see xref:docs/message-queue-algorithm.adoc#cancellation[Three ways to be cancelled].


[[manual-processing]]
==== Manual `Message<T>` processing

[WARNING]
====
Manually ending a message's lease is a delicate endeavor: exactly one of `successDelete` / `failureRequeue` / `failureDelete` must be called per message, `extend()` must be called before the lease expires if the work needs longer than `processingTimeout`, and every guarantee `process()` provides above — the correct write-back on every kind of failure, a lease kept alive automatically when the work needs more time, cancellation handled correctly — has to be reimplemented by hand instead of relied on.
Do this only when `workerPool` and `process()` genuinely cannot be used.
====

[cols="1,3",options="header"]
|===
| Member | Purpose

| `suspend fun successDelete(notes: JsonElement = JsonNull)`
| The work succeeded: deletes the message, recording `notes` alongside the success.

| `suspend fun failureRequeue(due: Instant? = null, notes: JsonElement = JsonNull)`
| The work failed: clears the lease and makes the message due again at `due` (immediately, by default), recording `notes` as this attempt's failure.
Defers to `failureDelete` instead when this was the last authorized attempt.

| `suspend fun failureDelete(notes: JsonElement = JsonNull)`
| Deletes the message and reports it as a failure, recording `notes` as the reason — regardless of how many tries remain.
Call it directly to abandon a message outright, whatever `maxTries` still allows.

| `suspend fun extend()`
| Re-stamps the lease, pushing `expiresAt` forward by another `processingTimeout` — for a handler that needs longer than the lease to finish.
|===

[source,kotlin]
----
val message = queue.receive()
try {
    sendEmail(message.payload)
    message.successDelete()
} catch (e: Exception) {
    message.failureRequeue(notes = JsonPrimitive(e.message))
}
----

Getting this wrong — never calling any of the three, or calling one on a lease that has already expired — is exactly the failure mode `process()` above exists to rule out.


== Core concepts — Cron

A cron fires a *tick* — one call to the handler — for a *window*, a half-open time range `[from, to)` the size of `interval`.
A window is *materialized* — turned from pure arithmetic on a schedule into an actual claimable row — once it has fully elapsed, then leased and run exactly like a message.


=== `CronSink`

[source,kotlin]
----
val cronSink = CronSink(
    source = dataSource.asSource(),
    tablesPrefix = "public.kcpt_",   // the default
)

val cleanup = cronSink.cron(
    name = "cleanup",
    config = Cron.Config(interval = 10.minutes),
    startAt = Clock.System.now(),   // the default
    runImmediately = false,         // the default
)
----

`startAt` and `runImmediately` only matter the first time a given name is ever registered — after that, restarting the application resumes whatever progress is already stored.


=== `Cron.Config`

[cols="1,2,3",options="header"]
|===
| Field | Default | Meaning

| `interval`
| _(required)_
| The wall-clock cadence: how wide one window is.

| `maxInterval`
| `interval * 50`
| The widest a single catch-up window may be, after downtime.

| `retries`
| `5`
| Failed attempts, including reclaims, before a window is dead-lettered.

| `tickTimeout`
| `interval`
| How long a lease is held before another server may reclaim it.

| `tickGrace`
| `max(tickTimeout * .2, 200ms)`
| Extra margin before a reclaim, so a handler's own timeout always fires first.
|===


=== `Cron.run()`

One call per server — every server calling `run()` runs the identical loop, and there is no leader:

[source,kotlin]
----
public suspend fun run(
    timeout: Duration = config.tickTimeout,
    onSuccess: (from: Instant, to: Instant, notes: JsonElement) -> Unit = { _, _, _ -> },
    onFailure: (failure: CronTickFailure) -> JsonElement = { JsonObject(it.defaultNotes()) },
    onDeadLetter: (from: Instant, to: Instant, notes: JsonElement) -> Unit = { _, _, _ -> },
    onError: (cause: Throwable) -> Unit = {},
    tick: suspend (from: Instant, to: Instant) -> JsonElement?,
): Nothing
----

`timeout` bounds the tick — freely longer than `tickTimeout`, since a tick's lease is kept alive automatically whenever it genuinely needs one, exactly like ``Message<T>.process()``'s own automatic keepalive: no parameter to configure, and nothing to misconfigure (see xref:docs/cron-algorithm.adoc#corner-timeout-above-lease[Running a handler for longer than its lease]).
`onError` reports an infrastructure failure — a dropped connection, an exhausted pool, a tick whose lease had already expired before it could even start — in the materialize/lease/write-back queries themselves, distinct from `onFailure`, which reports the handler's own failures.

`run()` never returns — cancel its coroutine to shut a server down.
See xref:docs/cron-algorithm.adoc#job-1-materialize[Job 1 — materialize] for exactly how a window's boundaries stay pinned to the grid rather than drifting with however long a handler takes.


== Shared primitives

=== `Source`

The library's entire database dependency — see <<a-source>> above.


=== `PGChannel<T>`

The `LISTEN`/`NOTIFY` primitive both feature modules build on, and the one piece of `kcpt-core` that is genuinely public API rather than internal plumbing:

[source,kotlin]
----
public class PGChannel<T>(
    public val name: String,
    private val serializer: KSerializer<T>,
    private val onUndecodableNotification: (channel: String, payload: String, cause: Throwable) -> Unit = { _, _, _ -> },
) {
    public suspend fun openListenConnection(scope: CoroutineScope, source: Source): ConnectionFlow<T>
    public suspend fun notify(connection: Connection, value: T)
}
----

Reach for it directly to build a notification channel of your own on the same database, alongside a message queue or a cron — a `ConnectionFlow<T>` is collected once, for as long as notifications are wanted, and shares one listening connection across every wait rather than opening a new one per call.


[[internalkcptapi]]
=== `@InternalKcptApi`

A handful of declarations — the JDBC transaction helper, the properties-table mechanism, the schema-init coalescing helper, the JSON codec the two feature modules share — have to be `public` so `kcpt-message-queue` and `kcpt-cron` can see them across the module boundary, but were never meant for outside use.
They are gated behind `@InternalKcptApi`, a `@RequiresOptIn` marker: using one without opting in is a compile error naming the annotation.
Ordinary use of `kcpt-message-queue` or `kcpt-cron` never touches this surface — if the compiler ever asks for that opt-in, it is a sign of having reached into cross-module plumbing rather than the library's intended public API.


== Guarantees

[cols="3,1",options="header"]
|===
| The message queue guarantees | Detail

| Each message is held by at most one consumer at a time.
| xref:docs/message-queue-algorithm.adoc#guarantees[↗]

| At-least-once delivery, retried until success or `maxTries`.
| xref:docs/message-queue-algorithm.adoc#guarantees[↗]

| A crashed consumer's message is redelivered within `processingTimeout + processingGrace`.
| xref:docs/message-queue-algorithm.adoc#guarantees[↗]

| A permanently failing message is dead-lettered rather than retried forever.
| xref:docs/message-queue-algorithm.adoc#guarantees[↗]

| A consumer learns of a new message on commit, not on a poll interval.
| xref:docs/message-queue-algorithm.adoc#guarantees[↗]
|===

[cols="3,1",options="header"]
|===
| The cron guarantees | Detail

| Each window is handed to at most one server at a time.
| xref:docs/cron-algorithm.adoc#guarantees[↗]

| Windows are contiguous and non-overlapping.
| xref:docs/cron-algorithm.adoc#guarantees[↗]

| Cadence follows the clock, not handler durations, as long as servers are available.
| xref:docs/cron-algorithm.adoc#guarantees[↗]

| A crashed server's window is picked up by another within `tickTimeout + tickGrace`.
| xref:docs/cron-algorithm.adoc#guarantees[↗]

| A permanently failing window is dead-lettered without blocking later windows.
| xref:docs/cron-algorithm.adoc#guarantees[↗]
|===

CAUTION: Neither guarantees *exactly-once* execution — if a handler succeeds but the write-back recording it fails, the lease eventually expires and the work runs again.
Handlers should be idempotent.
Both documents' own "Guarantees and non-guarantees" sections (xref:docs/message-queue-algorithm.adoc#guarantees[message queue], xref:docs/cron-algorithm.adoc#guarantees[cron]) list every non-guarantee and the corner case behind each one — FIFO ordering, completion order, clock skew, and more.
